# BITMIND ONBOARDING ARCHITECTURE DESIGN

**Phase:** F4 - Onboarding Architecture Design  
**Date:** 2026-06-16  
**Status:** DESIGN ONLY - NO IMPLEMENTATION  
**Scope:** Determine canonical onboarding architecture for ESP32, OLED, and future Bitmind hardware

---

## EXECUTIVE SUMMARY

**Recommended Architecture:** HYBRID MODEL - Dual-Path Onboarding

**Core Principle:** Different device types require different onboarding paths. ESP32 hardware devices use AP Provisioning with WebSocket self-registration. Web clients use Connect Miner modal with REST API pre-registration.

**Key Decisions:**
- **AP Provisioning** remains canonical for ESP32/OLED hardware
- **Connect Miner** transforms into web client onboarding only
- **QR Onboarding** becomes AP mode accelerator (not backend-driven)
- **Device Claim** rejected as unnecessary complexity
- **Worker Name** is canonical identity owned by firmware
- **Wallet Address** is canonical reward destination owned by firmware

## SECTION 1: CURRENT STATE ANALYSIS

### 1.1 Existing Onboarding Methods

#### Method A: AP Provisioning (ESP32 Hardware)

**Flow:**
```
Device boots without WiFi credentials
→ Device enters AP mode (SSID: Bitmind-Setup)
→ User connects to AP
→ User opens browser to http://192.168.4.1
→ User fills form: WiFi SSID, Password, Worker Name, Wallet Address
→ Device saves to Preferences NV storage
→ Device reboots
→ Device connects to user's WiFi
→ Device connects to WebSocket
→ Device sends device.register
→ Backend auto-registers device
→ Device becomes active
```

**Strengths:**
- Works without external dependencies
- User controls all configuration locally
- No backend dependency for initial setup
- Supports offline environments
- Canonical method specified in firmware architecture
- Firmware architecture compliant
- Protocol v1 compliant

**Weaknesses:**
- Requires manual WiFi network switching
- User must know WiFi credentials
- No mobile-first experience
- No backend-driven configuration
- No device claim/ownership model

**Technical Debt:**
- Firmware stores workerName and walletAddress but doesn't send in device.register (identified in F3.5 audit)
- Device ID format changed from 12 hex digits to 4 hex digits (potential registry mismatch)
- Message concatenation race condition (fixed with 500ms delay)
- Backend rejects unregistered ESP32 devices (misaligned with MODEL A)

---

#### Method B: Connect Miner (Web Client)

**Flow:**
```
User opens Bitmind UI
→ User clicks "Connect Miner"
→ Modal opens with form
→ User fills: Wallet Address, Worker Name, Device Type, Mining Mode
→ Frontend calls POST /api/miners/connect
→ Backend validates and registers device
→ Backend generates device ID (16-byte hex)
→ Backend emits miner_connected WebSocket event
→ Frontend connects WebSocket
→ Device sends device.register
→ Backend validates (already registered)
→ Device becomes active
```

**Strengths:**
- Mobile-friendly UI
- Backend-driven device management
- Real-time WebSocket updates
- Integrated with dashboard
- Good for virtual/testing devices

**Weaknesses:**
- Creates virtual devices (not real hardware)
- Requires backend connectivity
- Not suitable for pre-flashed ESP32 devices
- Duplicates device registration logic
- Device ID generated by backend (not hardware-based)
- Confusion: "Connect Miner" implies hardware connection but creates virtual device

**Technical Debt:**
- Hardcoded localhost URL (fixed in F3 audit)
- WebSocket connection order issue (fixed in F3 audit)
- No clear distinction between hardware and virtual devices
- Backend generates device ID instead of using hardware ID
- No device type validation (ESP32 vs web-client)

---

### 1.2 Duplication Analysis

#### Device Registration Duplication

**Path 1: ESP32 Hardware (MODEL A)**
- Device ID: Hardware-based (ESP32 EFuse MAC)
- Registration: WebSocket device.register
- Backend: Auto-registers on first connection
- Worker Name: User-provided in AP mode
- Wallet Address: User-provided in AP mode

**Path 2: Web Client (MODEL B)**
- Device ID: Backend-generated (16-byte hex)
- Registration: REST API /api/miners/connect
- Backend: Pre-registers via REST API
- Worker Name: User-provided in modal
- Wallet Address: User-provided in modal

**Duplication Issues:**
- Two different device ID generation methods
- Two different registration protocols
- Two different user interfaces
- No clear separation in backend
- DeviceRegistry doesn't distinguish device types
- WebSocket handler has special case for web-client-* devices

---

### 1.3 Technical Debt Summary

**Critical Issues:**
1. Backend rejects unregistered ESP32 devices (MODEL B enforced on MODEL A devices)
2. Firmware doesn't send workerName/walletAddress in device.register
3. Device ID format inconsistency (12 hex vs 4 hex vs 16-byte hex)
4. Message concatenation race condition (fixed with delay)
5. No device type distinction in backend

**Medium Issues:**
1. Connect Miner creates virtual devices but implies hardware connection
2. No clear ownership model
3. No device claim flow
4. QR onboarding not implemented (OLED firmware)
5. No backend-driven configuration (Phase B scope)

**Low Issues:**
1. AP mode password hardcoded (12345678)
2. No OTA update mechanism (Phase B scope)
3. No device factory reset flow
4. No device rename flow

### 2.1 OLED Onboarding Experience

#### Boot Sequence

```
Power On
→ Initialize Serial (115200 baud)
→ Initialize OLED (128x64, I2C 0x3C)
→ Display Bitmind Logo
→ Load Configuration from Preferences
→ Check WiFi credentials
→ Check registration flag
```

#### Decision Tree

**If WiFi credentials missing:**
```
→ Enter AP Mode
→ Display QR Code on OLED
→ Display setup instructions
→ Start web server on port 80
→ Wait for user configuration
```

**If WiFi credentials present:**
```
→ Connect to WiFi
→ Display "Connecting..." on OLED
→ Wait for connection (timeout: 30s)
→ If timeout → AP Mode + QR Display
→ If success → Continue to WebSocket
```

## SECTION 3: DEVICE CLAIM MODEL EVALUATION

### 3.1 Device Claim Flow (Proposed)

```
Device boots
→ Device registers with backend
→ Device appears as "Unclaimed" in dashboard
→ User sees unclaimed device
→ User clicks "Claim Device"
→ User confirms ownership
→ Backend assigns ownership to user
→ Device becomes "Claimed"
→ Mining enabled
```

### 3.2 Comparison with AP-Only Onboarding

#### AP-Only Onboarding (Current)

**Flow:**
```
Device boots
→ User configures via AP mode
→ Device registers with backend
→ Device becomes active immediately
→ Mining enabled immediately
```

**Advantages:**
- Simpler flow
- No additional steps
- Device ready immediately
- No ownership ambiguity
- User has physical possession = ownership

**Disadvantages:**
- No ownership verification
- No transfer mechanism
- No multi-user support
- No device inventory management

---

#### Device Claim Model (Proposed)

**Flow:**
```
Device boots
→ Device registers with backend
→ Device appears as "Unclaimed"
→ User claims device
→ Ownership assigned
→ Mining enabled
```

**Advantages:**
- Ownership verification
- Transfer mechanism possible
- Multi-user support
- Device inventory management
- Audit trail

**Disadvantages:**
- Additional step required
- Delay before mining starts
- More complex architecture
- Additional backend state
- Additional UI components

---

### 3.3 Evaluation Against Use Cases

#### Use Case 1: Personal Mining (Single User)

**AP-Only:** ✅ Ideal - User has device, configures it, mines immediately
**Device Claim:** ❌ Overhead - Unnecessary claim step for personal device

#### Use Case 2: Device Resale

**AP-Only:** ⚠️ Manual - Buyer must factory reset and reconfigure
**Device Claim:** ✅ Clean - Seller releases claim, buyer claims device

#### Use Case 3: Mining Farm Deployment

**AP-Only:** ⚠️ Manual - Each device configured individually
**Device Claim:** ✅ Automated - Devices auto-register, admin claims in batch

#### Use Case 4: Device Rental

**AP-Only:** ❌ Impossible - No ownership transfer mechanism
**Device Claim:** ✅ Supported - Claim transfer on rental period end

#### Use Case 5: Pre-Flashed Device Purchase

**AP-Only:** ✅ Ideal - User receives device, configures WiFi, mines
**Device Claim:** ⚠️ Confusing - Why claim device you just purchased?

---

### 3.4 Recommendation

**REJECT Device Claim Model for Phase A**

**Rationale:**
1. **Phase A Scope:** Device claim is not required for Phase A completion
2. **Physical Ownership:** User has physical possession = ownership (sufficient for Phase A)
3. **Complexity:** Adds unnecessary complexity to onboarding flow
4. **Use Cases:** Phase A focused on personal mining, not resale/rental
5. **Alternative:** Factory reset provides sufficient ownership transfer for Phase A

**Future Consideration (Phase B):**
- Re-evaluate device claim model for commerce features
- Consider for mining farm deployment
- Consider for device rental marketplace
- Consider for device resale marketplace

## SECTION 5: CANONICAL OWNERSHIP

### 5.1 Data Ownership Analysis

#### workerName

**Current Owner:** Firmware (Preferences NV storage)

**Source:** User-provided during AP mode setup

**Storage:**
- Firmware: Preferences NV storage (primary)
- Backend: DeviceRegistry (secondary, sync from firmware)

**Canonical Source:** Firmware

**Rationale:**
- User provides during onboarding
- Firmware stores persistently
- Firmware sends in device.register
- Backend syncs from firmware
- Single source of truth: firmware

**Recommended Architecture:**
- Firmware owns workerName
- Backend syncs from firmware
- Backend never modifies workerName
- User changes workerName via AP mode (factory reset + reconfigure)

---

#### walletAddress

**Current Owner:** Firmware (Preferences NV storage)

**Source:** User-provided during AP mode setup

**Storage:**
- Firmware: Preferences NV storage (primary)

**Canonical Source:** Firmware

**Rationale:**
- User provides during onboarding
- Firmware stores persistently
- Firmware sends in device.register
- Backend syncs from firmware
- Single source of truth: firmware

**Recommended Architecture:**
- Firmware owns walletAddress
- Backend syncs from firmware
- Backend never modifies walletAddress
- User changes walletAddress via AP mode (factory reset + reconfigure)

---

#### deviceType

**Current Owner:** Firmware (hardcoded in firmware)

**Source:** Firmware compile-time constant

**Storage:**
- Firmware: Compile-time constant
- Backend: DeviceRegistry (sync from firmware)

**Canonical Source:** Firmware

**Rationale:**
- Determined by hardware variant (Legacy vs OLED)
- Hardcoded in firmware
- Firmware sends in device.register
- Backend syncs from firmware
- Single source of truth: firmware

**Recommended Architecture:**
- Firmware owns deviceType
- Backend syncs from firmware
- Backend never modifies deviceType
- Device type is immutable

---

#### deviceId

**Current Owner:** Firmware (hardware-based)

**Source:** ESP32 EFuse MAC address

**Storage:**
- Firmware: Computed at boot (not stored)
- Backend: DeviceRegistry (key)

**Canonical Source:** Firmware

**Rationale:**
- Derived from hardware MAC address
- Unique per device
- Firmware computes at boot
- Backend uses as registry key
- Single source of truth: firmware

**Recommended Architecture:**
- Firmware owns deviceId (computed from MAC)
- Backend uses deviceId as registry key
- Backend never modifies deviceId
- Device ID is immutable

**Format:** `esp32-{upper4hex}{lower8hex}` (per BITMIND_FIRMWARE_ARCHITECTURE.md)

#### token

- Firmware syncs token from backend

**Recommended Architecture:**

#### configuration

### 5.2 Canonical Ownership Summary

| Field | Canonical Owner | Source | Storage | Sync Direction |
|-------|----------------|--------|---------|----------------|
| workerName | Firmware | User input (AP mode) | Preferences NV | Firmware → Backend |
| walletAddress | Firmware | User input (AP mode) | Preferences NV | Firmware → Backend |

### 5.3 Modification Rules

**Firmware-Owned Fields (workerName, walletAddress, deviceType, deviceId, configuration):**
- Backend NEVER modifies
- Backend ONLY syncs from firmware
- User modifies via AP mode (factory reset + reconfigure)
- Firmware is single source of truth

**Backend-Owned Fields (token):**
- Firmware NEVER modifies
- Firmware ONLY syncs from backend
- Backend can rotate token
- Backend is single source of truth

**Phase B Considerations:**
- Backend may push configuration via device.config
- Ownership field may be added
- Configuration sync may become bidirectional

## SECTION 7: RECOMMENDED ARCHITECTURE

### 7.1 Canonical Onboarding Architecture

**HYBRID MODEL - Dual-Path Onboarding**

**Path 1: ESP32/OLED Hardware (AP Provisioning + WebSocket Self-Registration)**

### 7.2 Onboarding Flow

#### ESP32/OLED Hardware Onboarding

```
1. Device boots without WiFi credentials
2. Device enters AP mode (SSID: Bitmind-Setup)
3. Device starts web server on port 80
4. Device displays setup instructions on OLED (if available)
5. Device displays QR code on OLED (if available)
6. User connects to Bitmind-Setup WiFi
7. User scans QR code OR opens browser to http://192.168.4.1
8. User fills setup form: WiFi SSID, Password, Worker Name, Wallet Address
9. Device validates form
10. Device saves to Preferences NV storage
11. Device reboots
12. Device connects to user's WiFi
13. Device connects to WebSocket (getbitmind.com:443)
14. Device sends device.register (deviceId, deviceType, firmwareVersion, capabilities, workerName, walletAddress)
15. Backend validates device.register
16. Backend auto-registers device (if not already registered)
17. Backend sends device.registered (status, deviceId, token, serverTime)
18. Device stores token
19. Device becomes active
20. Device starts mining
```

**Key Characteristics:**
- AP mode is canonical method
- WebSocket self-registration (MODEL A)
- Firmware owns configuration
- Backend syncs from firmware
- No REST API step required
- Suitable for pre-flashed devices

---

#### Web Client Onboarding (Add Virtual Device)

```
1. User opens Bitmind UI
2. User clicks "Add Virtual Device"
3. Modal opens with form
4. User fills: Wallet Address, Worker Name, Device Type (Virtual/Testing)
5. Frontend validates form
6. Frontend calls POST /api/miners/connect
7. Backend validates and registers virtual device
8. Backend generates device ID (virtual- prefix)
9. Backend emits miner_connected WebSocket event
10. Frontend connects WebSocket
11. Virtual device sends device.register
12. Backend validates (already registered)
13. Backend sends device.registered
14. Virtual device becomes active
15. Virtual device appears in dashboard
```

**Key Characteristics:**
- REST API pre-registration (MODEL B)
- Backend generates device ID
- Virtual device creation
- Testing/development purpose
- Clear distinction from hardware

### 7.4 Backend Responsibilities

#### WebSocket Handler (server/ws/handlers.js)

**ESP32 Device Registration (MODEL A):**
```javascript
register: (ws, data) => {
  const deviceId = data.deviceId;
  const isEsp32Device = deviceId && deviceId.startsWith('esp32-');
  
  // ESP32 devices: auto-register on first connection
  if (!isRegistered && isEsp32Device) {
    console.log("[WS] DEVICE_AUTO_REGISTERED deviceId=" + deviceId + " reason=ESP32_SELF_REGISTRATION");
    DeviceRegistry.register(deviceId, { 
      deviceType: data.deviceType || 'miner',
      workerName: data.workerName,
      walletAddress: data.walletAddress
    });
  }
  
  // Virtual devices: must be pre-registered via REST API
  if (!isRegistered && !isEsp32Device) {
    console.log("[WS] DEVICE_REJECTED_UNREGISTERED deviceId=" + deviceId);
    const errorMsg = deviceGateway.createDeviceError('AUTH_INVALID', 'Device must be registered via REST API before WebSocket connection');
    ws.send(JSON.stringify(errorMsg));
    return false;
  }
}
```

**Key Changes:**
- Auto-register ESP32 devices on first connection
- Reject unregistered virtual devices
- Extract workerName and walletAddress from device.register
- Pass to DeviceRegistry.register()

---

#### REST API Handler (server/api/routes.js)

**Virtual Device Registration (MODEL B):**
```javascript
router.post('/api/miners/connect', (req, res) => {
  const { walletAddress, workerName, deviceType } = req.body;
  
  // Generate virtual device ID
  const deviceId = 'virtual-' + crypto.randomBytes(8).toString('hex');
  
  // Register virtual device
  const result = DeviceRegistry.register(deviceId, {
    deviceType: deviceType || 'virtual_client',
    walletAddress: walletAddress || null,
    workerName: workerName || null
  });
  
  // Emit WebSocket event
  wsServer.emit('miner_connected', { deviceId, ... });
  
  res.json({ success: true, deviceId, ... });
});
```

**Key Changes:**
- Add virtual- prefix to device IDs
- Set deviceType to virtual_client
- Clear distinction from hardware devices
